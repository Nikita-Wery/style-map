# 2. VictoriaMetrics

**Критерий: VictoriaMetrics — 2 балла.** Выполнена установка single-node VictoriaMetrics через Helm в namespace `monitoring`. Основа — первые два шага [официального руководства](https://docs.victoriametrics.com/guides/k8s-monitoring-via-vm-single/): подключение Helm-репозитория и установка single-node chart. Grafana для этого задания не требуется.

Команды установки с текущим файлом values и именем релиза `vm-single`:

```bash
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm repo update
helm install vm-single vm/victoria-metrics-single \
  --namespace monitoring --create-namespace \
  -f k8s/monitoring/guide-vmsingle-values.yaml
```

Это команды воспроизведения установки. Выполненная команда `helm list -n monitoring` подтвердила релиз `vm-single` в namespace `monitoring`: revision **2**, status **deployed**, chart **victoria-metrics-single-0.49.0**, app version **v1.154.0**.

В `k8s/monitoring/guide-vmsingle-values.yaml` включён `server.scrape.enabled`, задан интервал сбора 15 секунд, настроены собственные метрики VictoriaMetrics, Kubernetes API, nodes, cAdvisor и job `kubernetes-pods` с `kubernetes_sd_configs: role: pod`.

В job Pod применяются relabel-правила:

| Аннотация Pod | Назначение |
|---|---|
| `prometheus.io/scrape: "true"` | Оставить Pod среди целей сбора |
| `prometheus.io/port` | Подставить порт метрик в адрес цели |
| `prometheus.io/path` | Задать HTTP-путь метрик |

Labels Pod переносятся в labels метрик; добавляются `kubernetes_namespace` и `kubernetes_pod_name`. Аннотации обрабатывает именно scrape-конфигурация VictoriaMetrics, а не Kubernetes самостоятельно. Pod IP динамические: VictoriaMetrics получает адреса и метаданные через Kubernetes API/service discovery и обновляет targets при изменениях. IP backend и exporter не требуется фиксировать вручную. Для discovery нужны доступ к API и соответствующие права service account.

# 3. Runtime/framework metrics

**Критерий: runtime/framework metrics — 2 балла.** В `pom.xml` подключены `spring-boot-starter-actuator` и `micrometer-registry-prometheus`. В `src/main/resources/application.yaml` открыты endpoints `health,info,prometheus`, задан отдельный management-порт **8081**. Основной HTTP-порт backend — 8080.

Endpoint метрик — `/actuator/prometheus`; в `src/main/java/ru/itis/stylemap/config/SecurityConfig.java` разрешён доступ к нему без аутентификации. В шаблоне Pod `k8s/05-backend.yaml` указано:

```yaml
prometheus.io/scrape: "true"
prometheus.io/port: "8081"
prometheus.io/path: "/actuator/prometheus"
```

Поток данных:

```text
Spring Boot → Actuator/Micrometer → :8081/actuator/prometheus
                                    ↓ HTTP scrape

```

Подключённый Actuator/Micrometer обеспечивает стандартные семейства JVM, процесса и HTTP: например, `jvm_memory_used_bytes`, `jvm_threads_live_threads`, `process_uptime_seconds`, `http_server_requests_seconds_count` и `http_server_requests_seconds_sum`. HTTP-ряды появляются при обработке запросов. Это семейства стандартной автоконфигурации; отдельно их значения в данной runtime-проверке не фиксировались. Сбор endpoint backend подтверждён наличием `stylemap_users_active = 1` в VictoriaMetrics с `job="kubernetes-pods"` и instance на порту 8081.

# 4. Business metrics

**Критерий: бизнес-метрики — 4 балла.** Реализованы шесть семейств метрик, то есть больше требуемых четырёх. Регистрация находится в `src/main/java/ru/itis/stylemap/metrics/StyleMapBusinessMetrics.java` и `src/main/java/ru/itis/stylemap/metrics/ActiveUserMetrics.java`. Имена ниже — экспортируемые Prometheus-имена; Micrometer преобразует точки в подчёркивания и добавляет суффиксы типов/единиц.

| Метрика | Тип | Смысл и место обновления | Обоснование типа |
|---|---|---|---|
| `stylemap_outfits_published_total` | Counter | Число успешных публикаций: `PostService.createPostWithDetails()`, после `postRepository.save()`, через `outfitPublished()` | Накопительное число событий публикации |
| `stylemap_ratings_submitted_total` | Counter | Число успешных отправок оценок, включая изменение существующей: `PostService.ratePost()`, после сохранения оценки и пересчёта агрегата | Считает события, а не текущее число строк оценок |
| `stylemap_follows_actions_total{action="followed"}` / `{action="unfollowed"}` | Counter | Подписки и отписки: `PostService.toggleFollow()`, после сохранения или удаления связи | Каждый вид действия накапливается отдельно; отписка не уменьшает счётчик подписок |
| `stylemap_users_registered_total` | Counter | Успешные регистрации через `AuthService.registerUser()`, после сохранения пользователя, токена и вызова отправки письма | Накопительное число регистраций по этому сценарию; не общее число аккаунтов и не число подтверждений |
| `stylemap_users_active` | Gauge | Число аккаунтов с `isActive = true`: `ActiveUserMetrics.refreshActiveUserCount()` вызывает `UserRepository.countActiveUsers()` | Текущее состояние может увеличиваться и уменьшаться; это активированные аккаунты, а не пользователи онлайн |
| `stylemap_outfits_publish_duration_seconds_*` | Timer | Длительность успешной публикации: Sample начинается в начале `createPostWithDetails()`, останавливается в обработчике успешного завершения транзакции | Timer хранит число измерений и длительности в секундах |

Timer экспортирует `stylemap_outfits_publish_duration_seconds_count`, `stylemap_outfits_publish_duration_seconds_sum` и `stylemap_outfits_publish_duration_seconds_max`. Гистограммные buckets и percentile-ряды отдельно не настроены. Замер включает выполнение публикации и время до обработчика завершения commit.

`StyleMapBusinessMetrics` регистрирует transaction synchronization и записывает Counter/Timer в `afterCompletion()` только при `STATUS_COMMITTED`. Rollback и ошибка commit не учитываются как успех. Если транзакции нет, запись выполняется сразу; при активной транзакции без synchronization запись пропускается. Ошибки записи метрик перехватываются и логируются, чтобы не нарушать бизнес-операцию.

Gauge читает `AtomicLong`, а не выполняет SQL при каждом scrape. Снимок обновляется на `ApplicationReadyEvent` и по расписанию: initial delay и fixed delay — 15 секунд. До первого успешного чтения экспортируется `NaN`; при ошибке БД сохраняется предыдущий успешный снимок. JPQL-запрос в `src/main/java/ru/itis/stylemap/repository/UserRepository.java` считает активированные аккаунты в read-only транзакции.

Высококардинальные labels с UUID, email, username или идентификаторами постов не используются. Единственный бизнес-label — `action` с двумя фиксированными значениями. При нескольких backend-репликах Gauge отражает одно общее сохранённое состояние БД; складывать такие ряды нельзя. Для данного приложения подходит:

```promql
max(stylemap_users_active)
```

# 5. PostgreSQL metrics

**Критерий: PostgreSQL metrics — 2 балла.** В `k8s/03-postgres.yaml` контейнер `postgres-exporter` добавлен sidecar-контейнером в Pod StatefulSet `postgres`. Используется образ `quay.io/prometheuscommunity/postgres-exporter:v0.20.1`, endpoint `/metrics` на порту **9187**.

Exporter подключается к `localhost:5432/stylemap`: контейнеры одного Pod разделяют сетевое пространство имён. `DATA_SOURCE_USER` и `DATA_SOURCE_PASS` берутся из существующего Secret `stylemap-secret`, ключи `DB_USER` и `DB_PASSWORD`. Они подставляются в `DATA_SOURCE_NAME`; значения секретов в отчёте не приводятся.

Аннотации шаблона PostgreSQL Pod:

```yaml
prometheus.io/scrape: "true"
prometheus.io/port: "9187"
prometheus.io/path: "/metrics"
```

VictoriaMetrics обнаруживает Pod и собирает метрики именно с exporter, а не с SQL-порта 5432. `pg_up = 1` означает, что exporter успешно взаимодействует с PostgreSQL. Пример метрики БД — `pg_database_size_bytes{datname="stylemap"}`: размер базы в байтах.

Runtime-проверка через API VictoriaMetrics подтвердила **`pg_up = 1`** с labels `app="postgres"`, `job="kubernetes-pods"`, `kubernetes_namespace="stylemap"`, `kubernetes_pod_name="postgres-0"` и instance на порту 9187. Это подтверждает связь exporter с PostgreSQL и его обнаружение и сбор через Kubernetes pod discovery. Запрос `pg_database_size_bytes{datname="stylemap"}` вернул **8378035 байт**, `job="kubernetes-pods"`, instance на порту 9187: метрики базы присутствуют в VictoriaMetrics. Значение размера относится к моменту проверки.

Это ресурсы контейнеров; PVC `requests.storage` — отдельные запросы дискового пространства.

# 9. Ограничения

- Counter/Timer хранят состояние в памяти backend и сбрасываются при перезапуске экземпляра. Для анализа приростов следует учитывать сбросы счётчиков.
- Gauge обновляется асинхронно и согласован с БД с задержкой; scrape читает кеш. При ошибках обновления снимок может устареть.
- Gauge нескольких реплик дублирует общее состояние: ряды нельзя суммировать, допустим `max(...)`. Между обновлениями значения реплик могут временно различаться.
- Unit-тесты не заменяют интеграционные проверки ограничений реальной БД, rollback, поведения JPA persistence и интеграции Kubernetes. Тестовый transaction manager не проверяет фактический commit PostgreSQL.

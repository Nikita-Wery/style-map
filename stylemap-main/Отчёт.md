# Отчёт

## 1. Доменная область приложения

StyleMap — клиент-серверное приложение для публикации и просмотра аутфитов, то есть образов с подобранной одеждой. Пользователь может разместить фото или видео, добавить описание, хештеги, перечень вещей и ссылки на магазины с ценами. Социальная часть включает оценки публикаций, подписки на авторов и просмотр их профилей. Предусмотрена конвертация цен через внешний сервис курсов валют.

Основной сценарий: пользователь регистрируется, подтверждает аккаунт и входит в приложение. Затем просматривает ленту и отдельные публикации либо создаёт собственную публикацию с медиа и вещами. Автор может изменить описание, хештеги и список вещей или удалить пост. Администратор имеет отдельные операции управления пользователями, постами и хештегами.

Наличие функциональности в коде не означает, что все её сценарии проверены: границы проверки Docker Compose приведены в разделе 9, Kubernetes — в разделе 10.

## 2. Архитектура приложения

Приложение разделено на клиентскую и серверную части. React работает в браузере; nginx отдаёт собранные клиентские файлы и проксирует запросы к серверу. Spring Boot принимает HTTP-запросы, проверяет права, выполняет бизнес-операции и обращается к PostgreSQL.

```text
Браузер: React
       |
       v
nginx: статика frontend и прокси
       |
       | HTTP/REST: JSON и multipart
       v
Spring Boot backend ---------> PostgreSQL
       |                       записи и связи
       v
Файловое хранилище медиа
./uploads на хосте -> /app/uploads в контейнере

Liquibase: одноразовый процесс -> схема PostgreSQL
```

В Docker Compose используются сервисы `frontend`, `backend`, `db` и `liquibase-migrations`. Из браузера API вызывается по тому же адресу, что и frontend: nginx передаёт запросы на `backend:8080`. Это позволяет использовать сессионную cookie и CSRF-защиту без отдельного адреса API в браузере. Реализация HTTP-клиента находится в `frontend/src/api/client.ts`, конфигурация прокси — в `frontend/default.conf.template`.

Доменные записи и связи хранятся в PostgreSQL. Бинарные фото и видео записываются в примонтированный файловый каталог backend. Схемой БД управляет Liquibase. В backend также сохранены серверные страницы Thymeleaf, но основной клиент для запуска через Compose — React.

## 3. Стек реализации

| Часть | Технологии и назначение |
|---|---|
| Backend | Java 25; Spring Boot 4.0.3; Spring MVC для HTTP/REST; Spring Security для аутентификации, ролей и CSRF; Spring Data JPA / Hibernate для хранения сущностей |
| Схема и сборка backend | Liquibase для миграций; Maven и Maven wrapper для зависимостей и сборки JAR |
| Frontend | React, TypeScript, Vite; React Router для маршрутов; Tailwind CSS для оформления |
| HTTP-сервер frontend | nginx: раздача собранной статики и проксирование запросов |
| База данных | PostgreSQL 17; `ltree` для путей хештегов и JSONB для ссылок на магазины |
| Окружение | Docker для образов; Docker Compose для совместного запуска сервисов; Kubernetes (Minikube) для локального развёртывания и проверки реплик |

Backend-зависимости описаны в `pom.xml`, frontend-зависимости — в `frontend/package.json` и `frontend/package-lock.json`.

## 4. Основные сущности доменной области

Модели находятся в `src/main/java/ru/itis/stylemap/entity/`.

| Сущность / таблица | Назначение и основные связи |
|---|---|
| `User` / `users` | Пользователь: UUID, имя, email, хеш пароля, роль `USER` или `ADMIN`, признак активности, данные профиля. `externalAuthId` предназначен для внешней аутентификации и допускает NULL при регистрации по паролю |
| `Post` / `posts` | Публикация: автор, описание, время создания, средняя оценка и количество оценок. Один автор имеет много постов; пост содержит медиа и вещи |
| `PostMedia` / `post_media` | Метаданные фото или видео: путь, исходное имя файла, MIME-тип и тип `IMAGE`/`VIDEO`. Каждая запись относится к одному посту; бинарные данные находятся отдельно |
| `OutfitItem` / `outfit_items` | Вещь из образа: название, бренд и набор ссылок на магазины. В ссылке представлены URL, цена и валюта; набор хранится в JSONB. Вещь принадлежит одному посту |
| `Hashtag` / `hashtags` | Название и иерархический путь типа `ltree`. Посты и хештеги связаны отношением «многие ко многим» через `post_hashtags` |
| `Rating` / `ratings` | Оценка поста пользователем от 1 до 10 с датами создания и изменения. Составной ключ из пользователя и поста ограничивает запись одной оценкой на эту пару |
| `VerificationToken` / `verification_tokens` | Код подтверждения, срок действия и связь с пользователем «один к одному». После успешного подтверждения запись удаляется |
| `UserFollows` / `user_follows` | Направленная подписка пользователя на другого пользователя. Составной ключ содержит подписчика и автора; хранится время создания связи |

Для медиа и вещей в `Post` применены каскадные операции JPA и `orphanRemoval`: удалённые из управляемой коллекции дочерние записи удаляются из БД. При редактировании поста список вещей заменяется содержимым запроса, а не дополняется предыдущими значениями.

## 5. CRUD

Требование CRUD выполнено для сущности `Post`. Все четыре операции проверены через настоящий HTTP API работающего приложения в Docker Compose, с запросами через nginx.

| Операция | HTTP-метод | Endpoint | Описание |
|---|---|---|---|
| CREATE | POST | `/api/posts` | Создание поста: multipart-поля `file` и `postData`; JSON содержит описание, хештеги и вещи |
| READ | GET | `/api/posts/{id}` | Получение описания, автора, медиа, хештегов и вещей |
| UPDATE | PUT | `/api/actions/posts/{id}` | Изменение автором описания, хештегов и списка вещей |
| DELETE | DELETE | `/api/actions/posts/{id}` | Удаление поста автором или администратором |

Лента доступна через `GET /api/posts/feed`. API требует аутентификацию; небезопасные HTTP-методы защищены CSRF. Права на изменение и удаление проверяются сервером.

Проверка включала два последовательных обновления списка вещей, удаление одной вещи и отправку пустого списка. Дублирования не возникло, количество записей в БД соответствовало ответам API. После удаления пост отсутствовал в БД; повторный запрос деталей не возвращал публикацию. Известное ограничение: такой запрос сейчас получает HTTP 400 вместо более подходящего 404.

В коде также имеются административные операции создания, просмотра, изменения и удаления пользователей, постов и хештегов. Изменение пользователя ограничено статусом активности. Для оценок реализовано выставление и изменение, для подписок — переключение подписки и отписки. Эти операции не заявляются как полностью проверенный CRUD всех сущностей; отдельно проверено административное удаление пользователя с токеном.

## 6. PostgreSQL и persistence

Данные доменной области сохраняются в PostgreSQL через Spring Data JPA и Hibernate. Миграции находятся в `src/main/resources/db/changelog/`, основной файл — `db.changelog-master.xml`.

При исходной проверке Docker Compose на пустой БД успешно применены 66 changeset-ов. Проверено наличие таблиц `users`, `posts`, `post_media`, `outfit_items`, `hashtags`, `post_hashtags`, `ratings`, `user_follows`, `verification_tokens`, а также служебных таблиц `databasechangelog` и `databasechangeloglock`. Финальная схема допускает NULL в `users.external_auth_id`. Позднее добавлена миграция `2026/10/09-01-local-admin.sql`, создающая активного локального пользователя `root` с ролью `ADMIN`; его вход проверен в Minikube.

В `docker-compose.yml` каталог PostgreSQL примонтирован как `./my_db_files:/var/lib/postgresql/data`. При пересоздании только backend база и записи поста сохранились; это проверено повторным HTTP-чтением и запросом к БД. Результат относится к обычной работе на одном Docker-хосте и не доказывает наличие резервного копирования.

Фото и видео хранятся в `./uploads`, примонтированном в `/app/uploads`. PostgreSQL содержит метаданные файлов и связи с постами, но не бинарные медиа. Доступность тестового медиа после пересоздания backend также проверена. Сохранность требует сохранения обоих каталогов хоста; операции с файловой системой и транзакция БД не образуют единую атомарную транзакцию.

## 7. Соответствие методологии Twelve-Factor App

Методология описывает двенадцать принципов организации серверного приложения. Ниже оценивается фактическая реализация, включая ограничения учебного окружения. Полное соответствие не заявляется.

### I. Codebase — Кодовая база

**Смысл.** Приложение имеет одну кодовую базу под контролем версий, из которой создаются экземпляры для разных окружений.

**Реализация и подтверждение.** Backend, frontend, миграции, Dockerfiles и Compose находятся в одном Git-репозитории. Образы собираются из этих исходников, а не требуют отдельно полученного готового JAR. Подтверждение: `pom.xml`, `src/`, `frontend/`, `Dockerfile`, `docker-compose.yml`.

**Границы.** Для передачи полного исходного кода может использоваться ZIP без служебного каталога `.git`; это способ доставки исходников, а не отдельная кодовая база.

### II. Dependencies — Зависимости

**Смысл.** Зависимости явно объявляются, а среда исполнения изолируется от неявных библиотек и инструментов компьютера разработчика.

**Реализация и подтверждение.** Java-зависимости объявлены в `pom.xml`; Maven wrapper фиксирует Maven 3.9.12 в `.mvn/wrapper/maven-wrapper.properties`. Frontend использует `package.json`, `package-lock.json` и `npm ci`. Dockerfiles предоставляют JDK для сборки, Node.js для frontend и отдельные среды исполнения. Java, Maven и Node.js на хосте не требуются.

**Границы.** Первичная сборка требует доступа к реестрам образов и репозиториям зависимостей. Теги базовых образов не закреплены digest-ами, поэтому побайтовая воспроизводимость во времени не гарантируется.

### III. Config — Конфигурация

**Смысл.** Значения, зависящие от окружения, включая параметры подключения и секреты, отделяются от кода и передаются через окружение процесса.

**Реализация и подтверждение.** `application.yaml` содержит placeholders для `DB_USER`, `DB_PASSWORD`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `MAIL_*`, `APP_MAIL_ENABLED`, `APP_STORAGE_UPLOAD_DIR` и других настроек. Compose передаёт необходимые значения через `environment`. `.env.example` содержит только фиктивные значения. Настоящие секреты не должны входить в комплект сдачи; локальный `.env` исключён правилами `.gitignore` и `.dockerignore` и не предназначен для архива. Значение каталога загрузки по умолчанию — `./uploads`, без пути конкретного компьютера.

**Ограничения.** Не все параметры размещения вынесены в `.env`: опубликованные порты, некоторые значения топологии и разрешённые origin-ы заданы в Compose. Spring Boot самостоятельно не читает `.env`; при запуске вне Compose переменные нужно экспортировать. Соответствие оценено как частичное.

### IV. Backing services — Сторонние службы

**Смысл.** База данных и внешние службы рассматриваются как подключаемые ресурсы, доступные по конфигурации, а не как часть процесса приложения.

**Реализация и подтверждение.** PostgreSQL работает отдельным сервисом, backend получает JDBC URL и учётные параметры. SMTP и Google OAuth настраиваются переменными окружения. URL валютного сервиса задан через `CURRENCY_API_URL` в `application.yaml`; `ClientConfig` создаёт HTTP-клиент по этому URL. Внешняя отправка писем и OAuth не нужны для старта с фиктивными параметрами.

**Ограничения.** `LocalFileStorageService` использует примонтированный каталог, а не независимую службу хранения. Замена провайдера OAuth или формата валютного API может потребовать изменений кода. Реальные SMTP, Google OAuth и валютный сервис не проверялись. В Compose для дополнительных параметров, не перечисленных в `environment`, требуется явно передать переменную контейнеру.

### V. Build, release, run — Сборка, релиз, запуск

**Смысл.** Сборка создаёт артефакт, релиз связывает его с конфигурацией, запуск исполняет подготовленный результат. Эти этапы должны быть разделены.

**Реализация и подтверждение.** Backend `Dockerfile` собирает JAR через Maven wrapper в JDK-слое, затем переносит его в JRE-образ. `frontend/Dockerfile` выполняет `npm ci` и сборку Vite, а финальный образ nginx содержит статику. Compose связывает образы с конфигурацией и запускает сервисы. Миграции выполняются сервисом `liquibase-migrations`; backend ждёт его успешного завершения и не запускает миграции повторно внутри процесса.

**Ограничения.** Нет отдельного реестра неизменяемых релизов с уникальными идентификаторами: `docker compose up --build` объединяет действия сборки и запуска одной командой. В Compose миграции читаются из исходного каталога хоста. Поэтому полная изоляция релизного артефакта не обеспечена.

### VI. Processes — Процессы

**Смысл.** Процессы приложения должны быть заменяемыми и не хранить долговременное состояние локально; общее состояние размещается во внешних ресурсах.

**Реализация и подтверждение.** Основное бизнес-состояние backend сохраняет в PostgreSQL. `Dockerfile` запускает отдельный Java-процесс, а JPA-репозитории работают с внешней БД.

**Ограничения.** Строгое соответствие отсутствует: HTTP-сессии находятся в памяти backend, загруженные файлы — в файловом хранилище. Перезапуск теряет сессии, хотя бизнес-записи сохраняются. Для надёжной многоэкземплярной реализации потребовались бы общие внешние сессии и объектное хранилище; в текущую архитектуру они не входят.

### VII. Port binding — Привязка портов

**Смысл.** Приложение предоставляет сервис через собственный слушающий порт, не требуя внедрения в отдельно установленный сервер приложений.

**Реализация и подтверждение.** Spring Boot запускает встроенный HTTP-сервер на 8080. nginx слушает 80 внутри frontend-контейнера. Compose публикует frontend как `3000:80`, backend как `8080:8080`, PostgreSQL как `5434:5432`. Соответствующие публикации находятся в `docker-compose.yml`; серверный образ объявляет `EXPOSE 8080`.

**Границы.** Для запуска опубликованные порты должны быть свободны. Внутри сети Compose nginx использует адрес `backend:8080`, а не адрес компьютера пользователя.

### VIII. Concurrency — Параллелизм

**Смысл.** Нагрузку увеличивают запуском дополнительных процессов соответствующих типов, а не опорой на один неизменяемый процесс.

**Реализация и подтверждение.** Compose разделяет frontend, backend, PostgreSQL и одноразовый процесс миграций. Такое разделение позволяет независимо управлять жизненным циклом компонентов. В одноузловом Minikube backend и frontend успешно масштабированы с одной до двух реплик: оба Deployment достигли 2/2 Ready, Service backend включал оба Pod. После масштабирования вручную проверены работа авторизованного интерфейса, повторные переходы и перезагрузки страниц.

**Ограничения.** Исходная проверка Compose использовала один backend. Проверка двух реплик в Minikube подтверждает только описанные ручные сценарии на одном узле: сессии остаются в памяти отдельных backend-процессов, а общий PVC медиа имеет режим ReadWriteOnce. Kubernetes Service обеспечивает маршрутизацию к репликам, но результаты не доказывают надёжность сессий при любых запросах, production-масштабирование или работу хранилища на нескольких узлах.

### IX. Disposability — Утилизируемость процессов

**Смысл.** Процессы должны запускаться и завершаться предсказуемо, чтобы их можно было заменять без потери долговременных данных; важна корректная обработка завершения.

**Реализация и подтверждение.** Backend запускается прямым `ENTRYPOINT` Java. Compose ждёт готовности БД, миграций и backend; healthcheck вызывает `/actuator/health/readiness`, включающий состояние БД. Backend был пересоздан через `docker compose up -d --force-recreate --no-deps backend`: записи и медиа сохранились вне его процесса.

**Ограничения.** Проверка не включала аварийное завершение во время загрузки файла или транзакции, нагрузочный тест остановки и измерение времени graceful shutdown. Сессии после замены процесса теряются; нулевое влияние на вошедших пользователей не заявляется.

### X. Dev/prod parity — Сходство окружений

**Смысл.** Разработка, проверка и развёртывание должны использовать максимально похожие зависимости и службы, уменьшая ошибки из-за различий окружений.

**Реализация и подтверждение.** Compose задаёт единое проверочное окружение: PostgreSQL 17, образы из исходников и конфигурацию через переменные. В локальном запуске также используется PostgreSQL; подмена его другой СУБД не требуется. Dockerfiles и npm lockfile снижают зависимость от настроек хоста.

**Ограничения.** Это учебное локальное окружение, а не проверенное production-развёртывание. Локальный запуск использует Liquibase 5.0.1 из `pom.xml`, Compose — образ 4.29; способы исполнения миграций различаются. При проверке отключалась доставка писем; реальные внешние службы не проверены. Сходство всех окружений не доказано.

### XI. Logs — Журналирование

**Смысл.** Приложение выдаёт журнал как поток событий; его сбор, хранение и ротацию выполняет окружение исполнения.

**Реализация и подтверждение.** `logback-spring.xml` содержит консольный appender и корневой уровень INFO, сохраняющий также WARN и ERROR. Файловые appender-ы отсутствуют. Вывод процесса собирает Docker; просмотр доступен через `docker compose logs backend`. В `application.yaml` SQL-вывод по умолчанию выключен и может включаться через `SHOW_SQL`.

**Границы.** Для работы приложения постоянные файлы логов не нужны. Политика долговременного хранения и ротации Docker-логов отдельно не настроена; это задача окружения.

### XII. Admin processes — Административные процессы

**Смысл.** Миграции и другие служебные операции выполняются отдельными одноразовыми процессами с согласованными конфигурацией и кодом приложения.

**Реализация и подтверждение.** `liquibase-migrations` использует те же параметры PostgreSQL и changelog-и проекта. После применения схемы процесс завершается; успешный код завершения является условием запуска backend в Compose. При исходной проверке административного удаления роль ADMIN назначалась подтверждённому пользователю через одноразовый запуск `psql`, затем выполнялся повторный вход. Теперь локальный активный администратор `root` создаётся миграцией Liquibase; в Kubernetes миграции выполняются отдельным Job.

**Ограничения.** Автоматическое создание `root` предназначено только для локальной разработки и демонстрации; при занятом имени или email миграция не меняет существующего пользователя. Миграции используют отдельный образ: в Compose исходники примонтированы, в Minikube changelog включён в образ Liquibase. Полностью единый неизменяемый релиз приложения не обеспечен. Административные HTTP-операции над пользователями являются бизнес-функцией, а не заменой одноразовых служебных процессов.

**Сводная оценка**

| Фактор | Соответствие | Примечания |
|---|---|---|
| I. Codebase | Да | Единая кодовая база |
| II. Dependencies | Да | Maven, wrapper, npm lockfile, сборка в Docker; без гарантии побайтовой воспроизводимости |
| III. Config | Частично | Секреты и настройки приложения в окружении; часть топологии фиксирована в Compose |
| IV. Backing services | Частично | Подключаемая БД и внешние интеграции; медиа зависит от файлового каталога |

## 8. Запуск

После распаковки исходников перейти в каталог, содержащий `docker-compose.yml`. Нужны Docker с Compose v2, доступ к интернету для первоначальной сборки и свободные порты 3000, 8080, 5434. Java, Maven и Node.js на хосте не нужны.

```bash
cp .env.example .env
# Для локальной регистрации без SMTP изменить в .env:
# APP_MAIL_ENABLED=false
# При необходимости задать собственные локальные параметры БД.
docker compose up --build -d
```

Frontend доступен на **http://localhost:3000**, backend — на **http://localhost:8080**. `.env.example` — безопасный шаблон с фиктивными параметрами. Реальные OAuth/SMTP данные не требуются для старта и локального осмотра приложения. Google-вход с фиктивными параметрами не работает; доставка писем по умолчанию включена и требует SMTP либо явного отключения для локальной проверки.

При `APP_MAIL_ENABLED=false` регистрация сохраняет неактивного пользователя и код, но не отправляет письмо. Для подтверждения код получают из локальной БД по процедуре README и вводят в форму `/confirm` или передают API. Подтверждение обычной регистрации не обходится, код не публикуется в логах. Для локального администрирования миграция Liquibase создаёт отдельного активного пользователя `root` с ролью `ADMIN`, не требующего регистрации и подтверждения почты.

Compose сначала запускает PostgreSQL, затем миграции, backend и frontend. Состояние завершившегося сервиса миграций `Exited (0)` нормально.

```bash
docker compose ps -a
docker compose logs backend liquibase-migrations
docker compose down
```

Каталоги `my_db_files/` и `uploads/` сохраняются на хосте. Не следует удалять их, если нужны данные. Изменение параметров БД в `.env` не меняет учётные данные уже инициализированной базы. В комплект сдачи должны входить исходники, конфигурации сборки, lockfile, wrapper, миграции, README, этот отчёт и `.env.example`; локальные `.env`, `.git/`, `.idea/`, `target/`, `node_modules/`, собранная статика, данные БД, медиа и логи исключаются.

## 9. Проверка

Исходная проверка выполнена на свежем Docker Compose окружении с фиктивными локальными параметрами; результаты ниже относятся к ней. Дополнительная проверка Minikube описана в разделе 10. Подтверждены:

- Сборка backend и frontend образов из исходников; TypeScript-проверка и production-сборка frontend.
- Старт пустого PostgreSQL, применение 66 Liquibase changeset-ов, завершение миграций с кодом 0, готовность backend и HTTP-доступность frontend.
- HTTP-проксирование nginx: неавторизованный `/api/auth/me` возвращает JSON 401, авторизованные запросы проходят к backend.
- При недоступном локальном SMTP регистрация возвращает ошибку и откатывает запись пользователя. При отключённой доставке сохраняются неактивный пользователь с NULL `external_auth_id` и токен; до подтверждения вход запрещён, после подтверждения вход успешен и токен удалён.
- Полный HTTP CRUD поста с медиа, вещами и хештегами. Два обновления сохраняли две вещи без дублирования, удаление одной оставляло одну, пустой список — ноль. Результаты сверялись с БД.
- Возврат полного поста без `MultipleBagFetchException` и `LazyInitializationException` в проверенных сценариях.
- Удаление через admin API пользователя с существующим verification token: обе записи удалены без ошибки внешнего ключа.
- После пересоздания только backend сохранились пост, его вещи и хештеги, а медиа осталось доступным по HTTP.

CRUD выполнялся через реальные HTTP-маршруты, а не прямыми SQL-изменениями постов. Прямой доступ к БД использовался для проверки схемы и результатов, получения локальных кодов подтверждения и первоначального назначения роли администратора.

Реальная SMTP-доставка, Google OAuth и внешняя валютная интеграция **не проверялись**. Интерактивные сценарии интерфейса в браузере не проходили исчерпывающую проверку. Результаты подтверждают описанные сценарии учебного окружения, но не означают полную проверку всех функций или готовность к production.

## 10. Развёртывание в Kubernetes (Minikube)

### 10.1. Архитектура Kubernetes

Развёртывание выполнено в namespace `stylemap` одноузлового Minikube. Используются следующие абстракции:

| Абстракция | Ресурсы и назначение |
|---|---|
| Namespace | `stylemap`: группирует ресурсы приложения |
| ConfigMap | `stylemap-config`: передаёт несекретную конфигурацию через окружение |
| Secret | `stylemap-secret`: передаёт чувствительные параметры; реальные значения не входят в отчёт и архив |
| PersistentVolumeClaim | `postgres-data` для данных БД; `backend-uploads` для загруженных медиа |
| Service | `postgres` и `backend` типа ClusterIP для внутренних соединений; `frontend` типа NodePort для доступа с хоста |
| StatefulSet | `postgres`: PostgreSQL 17 с одной репликой и постоянным томом |
| Job | `liquibase`: отдельный одноразовый процесс применения миграций |
| Deployment | `backend` и `frontend`: управление Pod приложения и изменение числа реплик; frontend содержит nginx и собранный React |

Манифесты: `k8s/00-namespace.yaml`, `k8s/01-configmap.yaml`, `k8s/02-secret.example.yaml`, `k8s/03-postgres.yaml`, `k8s/04-liquibase-job.yaml`, `k8s/05-backend.yaml`, `k8s/06-frontend.yaml`. В манифестах backend и frontend исходно имеют по одной реплике.

### 10.2. Взаимодействие сервисов

```text
Браузер
  |
  v
NodePort frontend:30080
  |
  v
frontend Deployment / nginx
  |
  | HTTP: backend.stylemap.svc.cluster.local:8080
  v
backend ClusterIP Service
  |
  v
backend Deployment -----> PVC backend-uploads (/app/uploads)
  |
  | JDBC: postgres:5432/stylemap
  v
postgres ClusterIP Service
  |
  v
PostgreSQL StatefulSet + PVC postgres-data
  ^
  |
Liquibase Job (через Service postgres)
```

nginx проксирует API и маршруты аутентификации на `backend.stylemap.svc.cluster.local:8080`. Backend подключается к PostgreSQL через Service `postgres`. Имена сервисов разрешаются кластерным DNS; IP отдельных Pod не фиксируются. Service backend направляет запросы к готовым backend-репликам.

### 10.3. Docker-образы в Minikube

| Компонент | Образ | Источник |
|---|---|---|
| Backend | `stylemap-backend:k8s-v1` | `Dockerfile` |
| Frontend | `stylemap-frontend:latest` | `frontend/Dockerfile` |
| Liquibase | `stylemap-liquibase:latest` | `Dockerfile.liquibase` |
| PostgreSQL | `postgres:17` | Готовый образ PostgreSQL |

Пользовательские образы доступны локально в Minikube; для них задан `imagePullPolicy: Never`. PostgreSQL использует `IfNotPresent`. Образы можно собрать непосредственно для Minikube из корня проекта:

```bash
minikube image build -t stylemap-backend:k8s-v1 -f Dockerfile .
minikube image build -t stylemap-frontend:latest -f frontend/Dockerfile frontend
minikube image build -t stylemap-liquibase:latest -f Dockerfile.liquibase .
```

Альтернатива — загрузить уже собранные образы с теми же тегами через `minikube image load`. Публикация пользовательских образов во внешнем registry для этой демонстрации не требуется.

### 10.4. Развёртывание и проверка состояния

Команды выполняются при выбранном контексте Minikube. После создания namespace и до запуска PostgreSQL должен быть отдельно создан `stylemap-secret` из приватных значений конкретного окружения. Файл `k8s/02-secret.example.yaml` — только безопасный шаблон: его нельзя применять поверх настоящего Secret. Поэтому используется явный список файлов, а не `kubectl apply -f k8s/`.

```bash
kubectl apply -f k8s/00-namespace.yaml
kubectl apply -f k8s/01-configmap.yaml
# Здесь stylemap-secret уже должен быть создан отдельно.
kubectl apply -f k8s/03-postgres.yaml
kubectl rollout status statefulset/postgres -n stylemap --timeout=180s

kubectl apply -f k8s/04-liquibase-job.yaml
kubectl wait --for=condition=complete job/liquibase -n stylemap --timeout=180s

kubectl apply -f k8s/05-backend.yaml
kubectl rollout status deployment/backend -n stylemap --timeout=180s
kubectl apply -f k8s/06-frontend.yaml
kubectl rollout status deployment/frontend -n stylemap --timeout=180s

kubectl get pods -n stylemap
kubectl get services -n stylemap
kubectl get pvc -n stylemap
minikube service frontend -n stylemap --url
```

Миграции завершаются до демонстрации приложения; в backend они отключены через `SPRING_LIQUIBASE_ENABLED=false`. Повторное применение уже завершённого Job не запускает его заново. Для повторного выполнения удаляют только Job `liquibase` и снова применяют его манифест; PostgreSQL и PVC сохраняют.

Frontend доступен с хоста через NodePort `30080`; адрес для браузера выдаёт `minikube service`. Если команда поддерживает туннель, её терминал оставляют открытым. Для входа используется локальный администратор `root`, созданный миграцией `2026/10/09-01-local-admin.sql`. Пароль в отчёте не приводится; в БД хранится хеш с префиксом `{bcrypt}`. Аккаунт активен и предназначен только для разработки, поэтому почтовая регистрация для доступа к администрированию не требуется.

В локальной Kubernetes-демонстрации доставка почты отключена (`APP_MAIL_ENABLED=false`). Проверка SMTP в Actuator связана с этим флагом, поэтому отсутствующий SMTP не делает общий health DOWN. Это не отключает остальные проверки здоровья. Secret должен содержать согласованные с ConfigMap настройки: при совпадении ключей backend использует значение из Secret, подключённого последним.

### 10.5. Масштабирование

Проверены команды увеличения числа реплик с одной до двух:

```bash
kubectl scale deployment backend --replicas=2 -n stylemap
kubectl scale deployment frontend --replicas=2 -n stylemap
kubectl rollout status deployment/backend -n stylemap --timeout=180s
kubectl rollout status deployment/frontend -n stylemap --timeout=180s
kubectl get deployments,pods -n stylemap
kubectl get endpointslices -n stylemap -l kubernetes.io/service-name=backend
```

Оба Deployment достигли 2/2 Ready; все четыре Pod приложения были Running/Ready. Service backend предоставлял endpoints обоих backend Pod. После масштабирования вручную проверены авторизованная работа UI, повторная навигация и перезагрузки страниц — в этом одноузловом тесте они продолжали работать.

Этот результат не устраняет ограничение сессий в памяти отдельных процессов и не доказывает production-надежность или работу на нескольких узлах. Повторное применение манифестов backend/frontend возвращает заданное в них число реплик к одному.

### 10.6. Постоянное хранение

PVC `postgres-data` хранит данные PostgreSQL и примонтирован в `/var/lib/postgresql/data`. PVC `backend-uploads` хранит медиа и примонтирован в `/app/uploads`. Эти claims объявлены отдельно от workloads: замена Pod или пересоздание только Deployment/StatefulSet не удаляет PVC. Удалять namespace, сами PVC или все ресурсы через `kubectl delete -f k8s/` для повторной демонстрации нельзя, если нужно сохранить данные.

Оба PVC используют ReadWriteOnce. Две backend-реплики работали с общим `backend-uploads`, поскольку были размещены на одном узле Minikube. RWO не означает эксклюзивный доступ одного Pod на этом узле; проверка не подтверждает совместное использование тома с нескольких узлов. Использование PVC также не доказывает наличие резервного копирования или защиты от потери узла.
